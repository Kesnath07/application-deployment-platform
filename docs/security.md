# Security

## Principles

1. **No long-lived credentials.** CI uses OIDC. Workloads use IAM roles. The database password lives only in RDS and Secrets Manager.
2. **Least privilege.** Every role is scoped to one environment's resources.
3. **Defence in depth.** Private subnets, chained security groups, TLS to the database, hardened containers.
4. **Nothing sensitive in Git, images or Terraform state.**

## Identity and access

| Principal | Used by | Can do |
|---|---|---|
| `<env>-github-deploy` | GitHub Actions jobs in the matching GitHub environment | Push to its ECR repo, register task definitions, update its ECS service, pass its two task roles to ECS |
| `<env>-ecs-task-execution` | ECS agent at task start | Pull from its ECR repo, write to its log group, read its database (and optional GitHub token) secret |
| `<env>-ecs-task` | The running application | Nothing. The app calls no AWS APIs. ECS Exec permissions are added only when `enable_execute_command = true` |

The task execution role uses a custom inline policy instead of the broad
`AmazonECSTaskExecutionRolePolicy`. Wildcard resources appear only for actions AWS cannot scope
(`ecr:GetAuthorizationToken`, `ecs:RegisterTaskDefinition`, `ecs:DescribeTaskDefinition`, the SSM
message channels for ECS Exec), and each one is commented in the code.

## Secrets

| Secret | Where it lives | How it reaches the app |
|---|---|---|
| DB username/password | Secrets Manager `<env>/database` (JSON) | ECS `secrets` → `DB_USERNAME`, `DB_PASSWORD` at container start |
| GitHub token (optional) | Secrets Manager, created by the operator | ECS `secrets` → `GITHUB_TOKEN` |
| Local dev password | `.env` (git-ignored) | docker compose |

- The password is generated by an `ephemeral "random_password"` resource and passed only to the write-only arguments `password_wo` and `secret_string_wo`. It never appears in plans or state.
- Rotation is explicit: increment `db_password_version`, apply, then force a new ECS deployment.
- Task definitions reference secret ARNs only, so the values are invisible in the ECS console and API.
- `.gitignore` excludes `.env*` (except `.env.example`), `*.tfvars` (except examples), `backend.hcl`, `*.tfstate*`, `.terraform/`, keys and certificates.

## Network

- The ALB is the only internet-facing component. Its ingress is limited by `alb_ingress_cidrs`.
- ECS tasks accept traffic only from the ALB security group.
- RDS sits in data subnets with no internet route, has `publicly_accessible = false`, accepts traffic only from the ECS security group, and enforces TLS with `rds.force_ssl = 1` (the app connects with `sslmode=require`).
- The VPC default security group is stripped of all rules.
- HTTPS with a TLS 1.2/1.3 policy and an HTTP→HTTPS redirect is enabled by setting `certificate_arn`.

## Containers

- Multi-stage build. The runtime image contains only the JRE and the application, with no build tools.
- Runs as UID 10001. Application files are root-owned and not writable by the process.
- ECS runs it with `readonlyRootFilesystem`. Only `/tmp` is writable (an ephemeral task volume).
- No secrets or environment-specific configuration are baked into the image.
- ECR scans on push. `IMMUTABLE` tags stop anyone from replacing a deployed image under the same tag.

## Application

- Input is validated at the edges: names, GitHub URLs, Docker tag syntax, with `latest` rejected.
- Status changes follow a strict state machine, so replayed or out-of-order callbacks cannot corrupt history.
- Errors return structured JSON without stack traces (`server.error.include-stacktrace=never`).
- `open-in-view` is disabled, and so is Actuator exposure beyond `health` and `info`.

## Accepted risks and next steps

| Risk / gap | Mitigation today | Next step |
|---|---|---|
| No authentication on the dashboard or API, including the status callback | Restrict `alb_ingress_cidrs` to a VPN or office range. It's an internal tool | ALB OIDC authentication (Cognito or corporate IdP), or Spring Security with SSO; signed callbacks |
| AWS-managed encryption keys instead of customer-managed KMS keys | Encryption at rest is still on (ECR AES256, RDS, Secrets Manager, CloudWatch) | Customer-managed KMS keys where compliance requires them |
| HTTP-only ALB in dev | Dev holds no sensitive data | Use an ACM certificate everywhere |
| Health probes can call any registered URL (SSRF surface) | Only http(s) URLs. Redirects are not followed. Egress is limited to ports 80/443 | Allow-list environment URLs to the ALB domains |
| No ALB access logs or VPC flow logs | CloudWatch metrics and application logs | Add an S3 log bucket and flow logs to CloudWatch |
| No WAF | Restricted ingress CIDRs | AWS WAF managed rule groups on the ALB |

Checkov runs in CI. Every suppressed check is listed in `.checkov.yaml` with the reasoning above.
